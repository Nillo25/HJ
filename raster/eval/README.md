# Оценочный набор: растровые планы cubicasa5k (80 планов)

Набор, на котором модуль растровых планов (PNG из `cubicasa5k`, челлендж Stoa «Make Blueprints Talk») сравнивал методы. Цель — сравнить другой подход на **тех же** картинках и вопросах.

## Что внутри

| Файл | Что это |
|---|---|
| `images/` | 80 PNG-планов, взяты как есть из `data/cubicasa5k/` превью-датасета Stoa |
| `questions.jsonl` | 1418 вопросов к этим планам: английские и финские. Каждый вопрос есть на двух языках с одинаковым ответом, то есть уникальных вопросов 709 |
| `our_results.csv` | наши ответы на 709 английских вопросов для каждого метода + правильный ответ |
| `subset_cubicasa_test_split.txt` | 27 планов из тестовой выборки CubiCasa5K — **честная** часть (см. ниже) |
| `subset_door_window_experiments.txt` | 20 планов, на которых подбирались правила для окон и дверей (на них цифры чуть оптимистичнее) |
| `LICENSE.md` | лицензия и авторы файлов cubicasa5k (CC BY-NC-SA 4.0). Атрибуцию сохранять при показе |

Поля `questions.jsonl` — как в исходном файле Stoa (`path`, `question`, `answer`, `unit`, `type`), плюс:
- `image` — путь к картинке внутри этой папки;
- `qtype` — тип вопроса (12 шаблонов: windows, doors, toilets, sinks, showers, saunas, kitchens, bedrooms, wc_rooms, bathrooms, balconies, floors);
- `cubicasa_test_split` — входит ли план в тестовую выборку CubiCasa5K.

## Как считать

- **Правило Stoa:** засчитывается только точное совпадение числа (`answer`).
- Финские вопросы дублируют английские, поэтому мы считали только английские (709). Если гонять оба языка, цифры не изменятся, просто каждый вопрос посчитается дважды.
- **Две цифры:**
  - **все 80 планов**;
  - **только test (27 планов, 217 вопросов).** Модель CubiCasa обучена на этом же датасете, поэтому на остальных планах она «видела» картинки. Честная цифра — по test. Для методов без CubiCasa (чистый LLM) разницы в утечке нет, но сравнивать удобнее на одних и тех же подмножествах.

### Методы

- **CubiCasa** — открытая модель CubiCasa5K (веса `model_best_val_loss_var.pkl`, инференс с 4 поворотами). Считаем связные области в масках комнат и значков. $0.
- **Haiku 5.5 / Opus 5.5** — Claude по картинке целиком, один вызов на план отвечает на все 12 типов сразу (structured output JSON). Effort `medium` (проверка дверей в гибриде — `low`). Промпт с определениями типов и словарём финских/шведских сокращений (MH, KH, SR, KÖK…).
- **Гибрид** — маршрутизатор по типу вопроса:
  - окна → CubiCasa;
  - двери → CubiCasa находит кандидатов, на плане рисуются пронумерованные рамки, Opus отмечает ложные и дописывает пропущенные;
  - остальные 10 типов → Opus.

### Уверенность гибрида

Ответы с `high` (совпали CubiCasa и Opus) верны в 94% случаев (395 из 422), `low` — 64%, `medium` — 35%.

## Что известно о трудных местах

- **Окна (~30% у всех методов).** Ошибка обычно ±1–2. На части планов разметка считает окно **по створкам**: секция между импостами — отдельное окно (например, `high_quality_architectural-13309`: 6 окон, у каждого импост, ответ 12). На других планах окно с импостом считается одним. Правило «по створкам» на 20 планах подняло точность с 20% до 40%, но на test упало до 15% — в гибрид не включено.
- **Двери** — считаются только проёмы с полотном (дугой); пустые проёмы — нет.
- **Души и ванны** — у CubiCasa нет класса «душ», поэтому там почти 0%.
- **Спальни** — VH (гардеробная) — не спальня.
- Текст на планах часто перевёрнут на 90°/180°. Бывают шведские планы, 2 этажа на одной картинке, сканы с правками от руки.

## Прогон решения HJ (YOLO-seg + чат) и сравнение

`run_hj.py` делает то же, что веб-интерфейс HJ: загрузка плана → `fp.infer.run` → каждый вопрос в `fp.chat.chat`. Код HJ не меняется. Число берётся из последнего вызова `count`, иначе из текста ответа.

```bash
# 1. окружение HJ (один раз)
cd <HJ> && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
# 2. веса модели HJ (v2) положить в <HJ>/runs/colab/v2_best.pt, ключ Anthropic — в <HJ>/.env
# 3. прогон (можно прерывать — продолжит с места остановки); сначала проверка на 2 планах:
cd <eval_set> && <HJ>/.venv/bin/python run_hj.py --repo <HJ> --model <HJ>/runs/colab/v2_best.pt --limit 2
<HJ>/.venv/bin/python run_hj.py --repo <HJ> --model <HJ>/runs/colab/v2_best.pt
# 4. сравнение
python3 compare.py predictions_hj.jsonl --name HJ --csv compare_hj.csv
```

Цена прогона HJ: Haiku 5.5 читает лист при загрузке (1 вызов на план) и разбирает вопрос, если не сработали правила. Ожидаемо — центы за весь набор. Модель HJ обучена на сплите train CubiCasa5K, поэтому колонка test честная и для неё.

### Результат прогона HJ (14.11.2026, веса `weights-v2`, все 80 / test)

| | HJ через UI (чат) | HJ direct (детектор + `count`, правильные классы) |
|---|---|---|
| ВСЕГО | 45.1% / 40.6% | 56.1% / 50.7% |
| окна | 43.8% / **48.1%** | 43.8% / **48.1%** |
| двери | 51.7% / 47.4% | 51.7% / 47.4% |
| раковины | 16.2% / 22.2% | 78.8% / 70.4% |

- Окна у YOLO HJ — лучшие среди всех методов (наши ~30%). Если в нашем гибриде брать окна от HJ: 80.0% → 81.9% (все), 76.5% → 78.8% (test).
- Разбор вопросов в чате HJ теряет ~11 п.п.: «sinks» → считает санузлы (в тексте есть «bathroom»), «separate WC rooms» → унитазы, «showers and bathtubs» → только ванны, «floors» и часть «balconies» — без числа; для окон/дверей срабатывает «подсветить» (число берём из ответа).
- Баг HJ: `fp/scale.py:62` `statistics.median` по пустому списку падает при загрузке плана (было на `high_quality_architectural-18`, `-1778`); `run_hj.py` повторяет загрузку без автомасштаба.
- Полные ответы: `hj_raw.jsonl` (UI), `hj_raw_direct.jsonl`; сравнение по вопросам: `compare_hj.csv`, `compare_hj_direct.csv`.

## Как сравнить свой метод

1. Ответить на вопросы из `questions.jsonl` (достаточно английских, `question` начинается с `How`).
2. Сравнить с `answer` на точное совпадение.
3. Посчитать точность по `qtype` на всех 80 и отдельно на `cubicasa_test_split == true`.
4. Сопоставить с колонками `our_results.csv` (`cubicasa`, `haiku_5_5`, `opus_5_5`, `hybrid`) по паре `image` + `qtype`.
