## Задача от Stoa

Программа отвечает на вопросы на естественном языке по строительным
чертежам и BIM-моделям — **точно и проверяемо**.

Их формулировка проблемы: универсальные модели отвечают по чертежам
уверенно и часто неверно, а инженер не может быстро проверить.

Просят решения, которые не устареют от следующих моделей: гибрид из
frontier-моделей, computer vision, 3D, геометрии, маленьких дообученных
моделей.

**Критерии, по 25% каждый:**
1. Точность ответов
2. Насколько решение визуализирует обоснование, чтобы человек проверил за секунды
3. Креативность
4. Низкая стоимость инференса

Приз: 1000 € + work trial в Stoa (Хельсинки, английский). 750 / 250 за 2-3 место.

Данные:

- полный 10 ГБ — `junction-dataset.zip`

## Что известно про датасет

**Превью (0,5 ГБ):** 1055 файлов — 374 JPG, 306 PNG, 123 PDF, 66 DXF,
20 DWG, 14 IFC, 10 SVG. 7990 вопросов к 320 из них.

**Полный (10 ГБ):** ~14 000 чертежей из Европы и США на ~30 языках,

Пример: «Сколько квартир на плане?» → 2, `count`.

объёмы — в пределах 2%; текст — свободная форма.

**Типы вопросов:** количество 76% (6076), площадь 20% (1599),
текст 3% (265), объём и длина меньше 1% (50).

**Источники (вопросы есть только у пяти из девяти):**

## Решение

Питч в одну строку: **«мы считаем, а не предполагаем»**.
Он закрывает сразу точность, проверяемость и стоимость.

Второй уровень питча: **каждый дефект данных превращён в способ
ответить.** Дубликаты форматов → путь к точности. Неподписанная площадь
→ счёт по контуру. Тридцать языков → ключ дедупликации. Нет масштаба →
вопрос пользователю в два клика.

### Маршрутизация по источнику

- **IFC** — запрос к модели (элементы, типы, этажи, количества).
  Точный ответ, цитата = GUID элемента. Библиотека `web-ifc` (WASM, Node).
- **Векторные (DXF / PDF)** — текст и геометрия с координатами.
  Площадь комнаты — по контуру формулой многоугольника, а не с подписи.
- **Растр** — единственный путь со зрением. Последним, по одному
  вырезанному фрагменту, не по всему листу.

LLM используется там, где без неё нельзя: понять вопрос и сформулировать
ответ. **Число она не производит.**

### Ключевые приёмы

**Извлекать один раз на картинку, а не на вопрос.** 7990 вопросов сидят
на 320 файлах. Один проход вытаскивает инвентарь плана (комнаты с
подписями и рамками, двери, окна) → в базу → все вопросы по этому плану
отвечаются из кэша. Кэш по хэшу файла, перезапуски бесплатны.

**Не просить модель считать — просить перечислить.** Структурированный
вывод: массив `{ label, box }`. Количество = длина массива, считает код.
Рамки для подсветки приходят бонусом.

**Словарь финских сокращений комнат:** WC, KPH (kylpyhuone), PH
(pesuhuone), S (sauna), MH (makuuhuone), OH (olohuone), K (keittiö), ET.

**Проверка цитаты кодом** между шагами цепочки: процитированный bbox
существует и содержит процитированный текст. Это и есть разница между
«проверяемо» и «врёт уверенно».

**Уверенность — из детерминированных сигналов**, не от модели: нашёл ли
текстовый поиск термин, сколько кандидатов-листов, прошла ли проверка
bbox, дал ли IFC точное совпадение. `confidence: 0.87` от модели не
защитить под вопросами.

### Масштаб

Нужен только площадям, объёмам и длинам — это 21% вопросов. Количество
и текст (79%) идут без него.

Порядок получения коэффициента пиксель→мм:
1. Размеры прямо отвечают (комната 3200 × 4100 → площадь умножением).
2. Калибровка по любому одному размеру (3200 мм = 160 px → 20 мм/px),
   считается раз на лист, кладётся в кэш.
3. Масштабная линейка.
4. Ничего → **вовлечь пользователя**: «кликни две точки и скажи
   расстояние». Это прямой совет инженера Stoa со стенда.

## Этапы (каждый демонстрируем сам по себе)

1. **Загрузка, индексация, текстовый поиск с подсветкой bbox. Без ИИ.**
   Уже показываемо: спросил — подсветилось место на листе.
2. **Путь IFC** (параллельно, на коллеге с опытом BIM-выгрузок) —
   точные ответы со ссылкой на элемент. 16% вопросов.
3. **Путь DXF / векторный** — 30% вопросов. Вместе с IFC это **46% без
   единого вызова зрения**.
4. **Растр** — перечисление с рамками, подсчёты (масштаб не нужен).
5. **Эвал-прогон и панель точности.**
6. *Если останется время:* архивный скан с калибровкой по клику — один
   слайд под критерий «не устареет от будущих моделей».

## Интерфейс

Критерии оценивают ответ, а не импорт. **Интерфейс загрузки не делать** —
индексация это консольный скрипт.

Весь бюджет в:
- **Просмотрщик листа с подсветкой.** Ответ слева, лист справа, клик по
  ответу перелетает к месту и обводит его. Это те самые 25%.
- **Панель точности.** Прогон по их вопросам: верно / неверно / отказ,
  процент ошибок, цена и время на ответ.

Дальше по пользе: панель «как нашёл» (трассировка маршрута), таблица
элементов из IFC с фильтрами, счётчик цены в шапке ответа, карта
датасета (что загружено, что честно не поддержано), расхождения модель vs
чертёж, лог отказов.

**Не строить:** 3D-вьювер модели.

## Эвал

Ответы в датасете есть → панель точности строится честно.

- Три корзины: верно / неверно / отказ.
- **Дедуплицировать по языку перед подсчётом** — один вопрос на 2–4
  языках, иначе проценты надуты и это заметят.
- Хвастаться долей **неверных**, а не точностью. Формулировка для питча:
  «отвечаем на 60% и ошибаемся в 2%, а не отвечаем на всё и ошибаемся в 30%».
- Проверить: правила сверки применять как у них — количество точно,
  площади в пределах 2%.

### swiss_dwellings — DXF разобран

Слои: `ROOM_OUTLINE`, `ROOM_TEXT`, `UNIT_OUTLINE`, `WALL`, `DOOR`,
`WINDOW`, `FIXTURE`, `ANNOTATION`. Комнаты — готовые `LWPOLYLINE`,
собирать из отрезков НЕ надо. **Координаты уже в метрах** («Masse in
Metern»), площадь полигона выходит в м² без всякого масштаба — сверено с
подписями на листе до сотых.

Правила, прогнанные по всем 65 файлам против их ответов:

| правило | точность |
|---|---|
| окна = `LWPOLYLINE` на `WINDOW` ÷ 3 | **100%** (65/65) |
| квартиры = число `UNIT_OUTLINE` | 84% (55/65) |
| двери = `ARC` на `DOOR` | 56% (37/65) |
| общая площадь = сумма всех `ROOM_OUTLINE` | 15% (10/65) |

Что чинить: двери — дуга есть только у распашных, считать устойчивее;
площадь — нужен фильтр «только пронумерованные внутренние помещения»
(подпись = номер вида 2.01…2.31, без балконов и шахт); квартиры —
посмотреть 10 промахов. Площадь квартиры A/B = сумма комнат внутри
соответствующего `UNIT_OUTLINE` (точка в полигоне).

Не решено: различить унитаз / раковину / ванну — всё на слое `FIXTURE`
(75 полилиний + 40 окружностей), классифицировать по форме и размеру.

### IFC — проверен через web-ifc в Node

Загрузка не проблема: **61 МБ за 511 мс**, 71 МБ за 457 мс.

Вопросы в основном **по этажам** («сколько дверей на плане `3.korrus`»),
а не по модели целиком. Раскладка элементов по этажам через
`IfcRelContainedInSpatialStructure` → **42 из 54 верно с первой попытки**.

Все 12 промахов — это `rooms (spaces)`: помещения привязаны к этажу через
**`IfcRelAggregates`**, а не через ContainedInSpatialStructure. Добавить
вторую связь → будет ~100%.

Стены считать как `IFCWALL` + `IFCWALLSTANDARDCASE` (проверено: 99 + 747
= 846 = их ответ).

«Сантехнические приборы» в `bsc-clinic_clinic-plumbing.ifc` — это
**`IfcFlowTerminal` = 119**, точное совпадение. Модель водопроводная,
архитектурных элементов в ней нет совсем.

Мелочь: у одного файла имя PDF не выводится из имени IFC простым
правилом (`kit-fzk-haus_...plan-02-dachgeschoss.pdf`) — нужна таблица
соответствий.
